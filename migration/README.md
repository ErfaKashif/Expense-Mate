# SQLite → PostgreSQL migration

`migrate_sqlite_to_postgres.py` copies the Assignment 01 SQLite database
(`app/data/expensemate.db`) into PostgreSQL and checks that the copy is correct.
You can run it again safely: it never writes to the SQLite file, and it will not
overwrite a PostgreSQL database that already has data unless you pass `--replace`.

## 1. One-time PostgreSQL setup

```bash
sudo -u postgres psql
```

```sql
CREATE ROLE expensemate LOGIN PASSWORD 'choose-a-password';
CREATE DATABASE expensemate      OWNER expensemate;   -- application data
CREATE DATABASE expensemate_test OWNER expensemate;   -- automated tests only
```

```bash
cp .env.example .env      # then put the password into DATABASE_URL / TEST_DATABASE_URL
pip install -r requirements.txt
```

## 2. Run the migration

```bash
python migration/migrate_sqlite_to_postgres.py --report docs/evidence/migration_verification.md
```

| Option | Meaning |
|---|---|
| `--sqlite PATH` | Source SQLite file (default `app/data/expensemate.db`) |
| `--target-env NAME` | Environment variable that holds the target URL (default `DATABASE_URL`) |
| `--replace` | Target already has data: clear the PostgreSQL tables and copy again |
| `--report PATH` | Also save the verification table as Markdown |

Exit codes: `0` = committed and verified, `1` = failed and rolled back, `2` = refused
because the target already has data.

## 3. What the script does

1. Opens SQLite with `mode=ro`, so the file is never modified, and records its SHA-256 checksum.
2. Runs `PRAGMA integrity_check` and `PRAGMA foreign_key_check`.
3. Converts each value to the matching PostgreSQL type (table below).
4. Creates the schema by running the application's own migration files
   (`app/backend/database/migrations/*.sql`). The app and the script share one schema definition.
5. In a single PostgreSQL transaction it:
   - inserts every row with its original primary key, so foreign keys still match;
   - moves the identity sequences past `MAX(id)`;
   - verifies the copy: row counts, a column-by-column comparison of every row,
     money totals per user/type/currency computed independently by each database,
     a check for orphaned foreign keys, and a check of the next generated id.
6. Commits only if every check passes. On any failure it rolls back, so PostgreSQL ends up unchanged.
7. Compares the SQLite checksum again to confirm the original file was not touched.

## Type mapping

| SQLite (Assignment 01) | PostgreSQL (Assignment 02) | Note |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | "BY DEFAULT" lets the script keep the original ids |
| `REAL` (money) | `NUMERIC(14,2)` | Exact decimals. The script warns if any value would be rounded |
| `TEXT` date `YYYY-MM-DD` | `DATE` | An invalid date stops the migration |
| `TEXT` `datetime('now')` | `TIMESTAMP DEFAULT now()` | |
| `strftime('%Y-%m', date) = ?` | `date >= first_day AND date < next_month` | Can use the `(user_id, date)` index |
| `?` placeholders | `%s` placeholders (psycopg) | |
| `cursor.lastrowid` | `INSERT ... RETURNING id` | |
| `INSERT ... ON CONFLICT ... excluded.x` | same syntax (PostgreSQL 9.5+) | |
| `PRAGMA foreign_keys = ON` per connection | always enforced | |
