# Migration Report: SQLite → PostgreSQL

**Project:** ExpenseMate · **Course:** Software Construction & Development (SE-5B) · **Assignment 02**
**Owner:** 24K-3010 Erfa Kashif · **Script:** `migration/migrate_sqlite_to_postgres.py`

## 1. Before state (Assignment 01, SQLite)

- Database: one file, `app/data/expensemate.db`, accessed with Python's built-in `sqlite3` module.
- Schema: created at start-up by `Database.init_schema()` in `app/backend/db.py`. Five tables: `users`, `categories`,
  `transactions`, `budgets`, `settings`.
- Types: money was stored as `REAL` (binary floating point), and dates and timestamps as `TEXT`.
  Foreign keys were only enforced because every connection ran `PRAGMA foreign_keys = ON`.
- Connections: every one of the 21 `Database` methods opened and committed its own connection. A service could
  not group several writes into one transaction. For example, "insert expense" and "update the budget balance"
  committed separately.
- Configuration: the file path was hard-coded, with an optional `EXPENSEMATE_DB` override.
- Data at migration time: users = 2, categories = 11, transactions = 12, budgets = 3, settings = 0.

## 2. Target state (Assignment 02, PostgreSQL 16)

- Driver: **psycopg 3** (`psycopg[binary]`), using `dict_row` rows and `%s` parameter placeholders.
- Configuration: `DATABASE_URL` (application) and `TEST_DATABASE_URL` (tests) are read from the environment or a
  git-ignored `.env` file. `.env.example` documents them and holds no real secrets.
- Schema: versioned SQL files in `app/backend/database/migrations/` (`001_initial_schema.sql`), applied by
  `apply_migrations()`. That function is idempotent, records each version in `schema_migrations`, and uses an
  advisory lock so several workers can start at the same time.
- Types: `NUMERIC(14,2)` for money, `DATE`/`TIMESTAMP` for time values, `INTEGER GENERATED BY DEFAULT AS IDENTITY`
  primary keys, all original foreign keys (including `ON DELETE CASCADE`), all `CHECK` and `UNIQUE` constraints.
  It also adds a `month` format check and an index on `transactions(user_id, date)`.
- Transactions: `Database.transaction()` shares one connection per thread, so a service can commit or roll back
  several repository calls as one unit.

## 3. Reason for migration

1. **Concurrency.** SQLite locks the whole file for each write. PostgreSQL handles many simultaneous users through
   row-level locking (MVCC).
2. **Correct money arithmetic.** `NUMERIC` stores exact cents. `REAL` cannot (`0.1 + 0.2 ≠ 0.3`).
3. **Real data types and enforced integrity.** Real `DATE` values, and constraints that are always on.
4. **Deployability.** A file inside the app folder disappears on serverless or container hosts (the project has
   `api/index.py` for Vercel). A managed PostgreSQL server persists independently of the app.
5. **Separation of credentials from code.** Connection details now come from environment variables.

## 4. Implementation procedure

1. Create the role and the databases (`expensemate`, `expensemate_test`). See `migration/README.md`.
2. `cp .env.example .env` and fill in the URLs.
3. `python migration/migrate_sqlite_to_postgres.py --report docs/evidence/migration_verification.md`

The script then:

1. opens SQLite **read-only** (`mode=ro`) and records its SHA-256 checksum;
2. runs `integrity_check` and `foreign_key_check`;
3. converts the types (see the table below);
4. creates the schema from the application's own migration files, so there is one source of truth;
5. in **one PostgreSQL transaction**, copies all rows with their original ids, resets the identity sequences, and
   verifies the copy;
6. **commits only if every check passes**, otherwise rolls back.

| Compatibility issue | SQLite | PostgreSQL / how it was handled |
|---|---|---|
| Auto-increment keys | `AUTOINCREMENT` | `IDENTITY BY DEFAULT`. Original ids are inserted explicitly, then `setval(MAX(id)+1)` |
| Money | `REAL` | `NUMERIC(14,2)`. Values are converted via `Decimal(str(x))` and the script warns if any are rounded (none were) |
| Dates/timestamps | `TEXT` | `DATE`/`TIMESTAMP`. An invalid date **aborts** the migration |
| Month filter | `strftime('%Y-%m', date) = ?` | `date >= first_day AND date < next_month` (can use the index) |
| Placeholders / new id | `?`, `cursor.lastrowid` | `%s`, `INSERT … RETURNING id` |
| Upsert | `ON CONFLICT … excluded.x` | same syntax, kept |
| Row values returned | `str`/`float` | `Decimal`/`date`/`datetime` are converted back to the old API formats in `models/` (amounts as numbers, `YYYY-MM-DD`, `YYYY-MM-DD HH:MM:SS`), so the frontend is unchanged |
| Schema bug | `remaining_amount … CHECK (amount >= 0)` (the check tested the wrong column) | no check on the legacy column: a negative remaining value is legitimate |
| Case-sensitive data | `'erfa '` (trailing space), `'food'` and `'Food'` | copied byte-for-byte. Nothing is "cleaned" during migration |

## 5. Data preservation

Every row of every table is copied with the same primary key, so all relationships are preserved. The original
SQLite file is never written: it is opened read-only and its checksum is compared before and after
(`d985437f…28a6` both times). The script refuses to overwrite a non-empty target unless `--replace` is given. The
legacy `budgets.remaining_amount` values are preserved, even though the application no longer relies on them
(see the rewriting report).

## 6. Risks and mitigation

| Risk | Mitigation |
|---|---|
| Partial copy after an error | Single transaction with rollback. Tested: a corrupt row means 0 rows in PostgreSQL afterwards (`test_failure_rolls_back_everything`) |
| Precision loss | Exact `Decimal` conversion, rounding warnings, money totals compared per user/type/currency |
| Id collisions with new rows | Sequences reset and verified ("next id" checks); a new expense after migration got id 37 = max + 1 (tested) |
| Accidental double run / overwrite | Exits with code 2 ("refused") unless `--replace` is given |
| Credentials leaking | URLs only in `.env` (git-ignored); passwords masked in logs and reports |
| Damaging the source | Read-only open plus a checksum comparison |
| Tests wiping real data | Tests use only `TEST_DATABASE_URL`, and refuse to run if the name lacks "test" or equals `DATABASE_URL` |
